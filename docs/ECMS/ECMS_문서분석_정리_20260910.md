## 3. 설계의 핵심 — 2트랙 구조

| 구분 | 트랙 A — 사용자 주도 | 트랙 B — 시스템 주도 |
|---|---|---|
| 시점 | 결제 직후 (즉시) | 매일 새벽 배치 (기본 04:00) |
| 수행 주체 | 현장 · 직원 | 시스템 |
| 내용 | 영수증 촬영, 현장코드 · 계정과목 · 목적 · 인원 입력 후 제출 | 카드 승인내역 수집 후 트랙 A 건과 자동 매칭 |
| 역할 | 즉시성 확보 (기억과 영수증이 살아있는 유일한 시점) | 검증 및 누락 탐지 (제출하지 않은 지출 적발) |

두 트랙은 자동 매칭 지점에서 합류하고, **그 이후에 회계담당자의 단일 검토가 한 번**
일어난다.

### 왜 "결제 즉시 승인요청"이 아닌가 (문서에 명시된 근거)

1. 이미 결제가 완료된 뒤이므로 반려해도 지출은 발생한 상태다. 반려의 실질은
   개인 부담 환수 또는 계정 재분류에 그친다.
2. 결제 시점에는 카드 승인내역이 없어 OCR 값만 있는 미검증 상태이며,
   담당자에게 불완전한 근거로 판단을 요구하게 된다.
3. 이후 카드내역이 도착해 금액이 어긋나면 담당자가 같은 건을 두 번 보게 된다.
4. 현장 결제는 새벽과 주말에도 발생하므로 담당자 상시 대기는 불가능하다.
5. 결제 시점의 통제는 사후 승인이 아니라 **사전 통제**(카드 한도, 업종 차단,
   고액 건 사전신청)로 건다. 이는 시스템이 아니라 **카드사 설정**에서 거는 편이
   훨씬 강력하다.

### 부수 효과 — 장애 내성

연동이 끊겨도 트랙 A는 영향받지 않아 지출 등록이 계속된다. 제출 건은 SUBMITTED로
누적되고, 복구되면 **롤링 조회(기본 14일)** 가 밀린 구간을 자동으로 대사한다.
별도 복구 작업이 필요 없다. 스캔이 진입점인 구조였다면 연동 중단 시 모든 지출
등록이 멈췄을 것이다.

## 4. CODEF 제약 — 설계값이 여기서 나온다

실조사로 확정된 사실이며, 이후 설계값(배치 시각, 조회 범위, 매칭 키)이 전부
여기서 파생된다.

| 제약 | 내용 | 설계 반영 |
|---|---|---|
| **실시간 Push 없음** | 공개 자료에 Webhook/Push 계약 없음. 조회형 API뿐 | 즉시성은 트랙 A가 담당. Push 전제 설계 금지 |
| **중복로그인 차단** | 국민·현대·NH·비씨·씨티·우리·롯데·하나·전북·광주·제주 불가 (삼성·신한·수협만 가능) | 배치는 업무시간 외 새벽 수행. 조회 전용 부계정 검토 |
| **IP 차단 경고** | 개발가이드에 "배치형 서비스로 간주 시 이용 제한" 명시 | `inquiryType="1"` 전체조회 1회 호출, 재시도 1회 제한 |
| **`memberStoreInfoType="3"` 필수** | 기본값 `"0"` 이면 가맹점 사업자번호·업종·주소·부가세가 **전부 빈 값** | 미지정 시 국세청 연동과 불공제 자동판정이 통째로 무력화 |
| **당일 조회 = 비씨만** | 제공돼도 가맹점 상세 없음, 전체조회 불가, 명세 최종 갱신 2021-09 | 정본은 일반 승인내역 API. 비씨 사용 시 보조로만 |
| **조회 가능 기간 상이** | 삼성·롯데·현대 3개월 / 신한 6개월(1주 단위) / 국민·우리·하나·NH 12개월 / 비씨 2년 | 초기 적재 범위가 카드사에 종속. 1회 범위 초과 시 자동 분할 → 호출 수 증가 |
| **승인번호 단독 키 불가** | 7~8자리로 짧고 재사용됨. 신한은 승인번호 없는 건을 응답에서 제외 | 매칭 키에서 제외, 보조 검증 용도로만 |

### 카드사 미확정 대응

카드사가 아직 정해지지 않았으므로 **기관코드 · 로그인방식 · 조회 가능 기간 ·
당일조회 지원 여부 · 중복로그인 제약을 전부 `card_config` 설정값으로 흡수**하는
설계다. 카드사가 확정되면 설정만 바꾸면 되도록 했다.

### 공급원 추상화

`fetchApprovals(기관코드, 시작일, 종료일, 카드식별자?)` 인터페이스로 수집 계층을
분리한다. CODEF 구현체는 커넥티드아이디 관리와 카드사별 파라미터 분기를 내부에
감추고, EDI 구현체는 파일 수신·파싱을 내부에 감춘다. 상위 매칭 엔진은 표준
스키마(카드끝4자리, 승인일시, 금액, 가맹점명, 가맹점사업자번호, 업종, 부가세,
승인번호, 결제방법, 할부개월, 취소여부, 취소금액, 매입여부, 매입일자,
국내외구분, 원본응답)만 안다.

## 6. 처리 로직

### 6.1 수집 배치 (10단계)

배치 기록 생성 → 조회 범위 산정(롤링, maxLookback 초과분 절단) → 범위 분할
(신한 7일·비씨 30일 등) → 전체조회 또는 카드별 순회 → `memberStoreInfoType="3"`
지정 → 표준 스키마 정규화 후 upsert(키: 기관+카드끝4자리+사용일시+금액+승인번호)
→ 기존 건은 취소여부·취소금액·매입여부만 갱신하고 원본은 이력 보관 →
건전성 검사 → 매칭 엔진 호출 → 완료 기록 (실패 시 재시도 1회 후 관리자 알림)

**배치 설계 원칙 4가지**
- 새벽 고정 (중복로그인 충돌 회피)
- 재시도 1회 제한 (오류 건은 과금되지 않으나 과도한 재시도는 IP 차단 사유)
- 롤링 조회 범위는 자동 복구 장치
- **배치가 실패한 날은 미제출 독촉 카운트를 진행시키지 않는다** — 시스템 장애로
  사용자가 독촉받아서는 안 된다

### 6.2 자동 매칭

사용자 입력 시각과 카드 승인 시각은 정밀도가 다르다(사용자는 촬영 시점 기준).
따라서 매칭 키는 승인일시가 아니라 **결제일자**를 쓴다.

| 단계 | 조건 | 결과 |
|---|---|---|
| 1차 (정확) | 카드끝4자리 + 결제일자 일치 + 금액 정확 일치 | 후보 1건이면 자동 매칭 |
| 2차 (일자 오차) | 카드끝4자리 + 결제일자 ±1일 + 금액 정확 일치 | 후보 1건이면 자동 매칭 |
| 3차 (보조 검증) | 후보 2건 이상이면 승인번호 또는 가맹점명 유사도 | 단일 확정 시 자동 매칭 |
| 실패 | 후보 없음 또는 판별 불가 | `MANUAL_MATCH` 로 이관 |

- 매칭 성공 시 **금액·가맹점명은 카드내역 값이 정본**, 사용자·OCR 값은 이력 보존
- **금액이 다르면 자동 매칭하지 않는다** — 부분취소·분할결제 가능성이 있어
  사람이 판단
- 매칭되지 않은 카드내역은 제출 기한(기본 3일) 경과 시 `UNSUBMITTED` 전환

### 6.3 룰엔진 자동 플래그

| 코드 | 플래그 | 판정 조건 | 기본 동작 |
|---|---|---|---|
| F01 | 불공제 업종 | 유흥·골프·면세 등 | 담당자 검토 |
| F02 | 휴폐업·간이과세 | 국세청 상태조회 결과 | 담당자 검토 |
| F03 | 심야 사용 | 22시~06시 | 담당자 검토 |
| F04 | 주말·공휴일 | 토·일 또는 공휴일 | 담당자 검토 |
| F05 | 금액 임계 초과 | 건당 설정값 초과 | 담당자 검토 |
| F06 | 동일 가맹점 반복 | 7일 내 동일 가맹점 3회 이상 | 담당자 검토 |
| F07 | 현장 미배정 | siteCode 없음 | **사용자 보완** |

| F11 | 영수증 분실 등록 | 영수증 없이 사유 기재 | 담당자 검토 |

> **무플래그 건은 자동승인 또는 일괄승인 대상**으로 분류한다. 이 처리를 적용하지
> 않으면 담당자가 전건을 수기 검토하게 되고 결국 시스템이 사용되지 않는다.
> 적용 여부는 S-03 화면에서 설정.

### 6.4 OCR

이미지 업로드 후 **비동기** 요청 → 금액·가맹점명·사업자번호·공급가액/부가세·품목
추출 → 사용자 화면 자동채움(수정 가능) → 매칭 후 카드내역과 대조하여 불일치 기록(F08)

- **OCR은 보조 수단이다. 어떤 경우에도 진행을 차단하지 않는다.**
- **품목 내역은 카드 승인내역에 없는 유일한 정보**이므로 추출 우선순위 최상
- 정확도 목표를 100%로 두지 않는다 — 영수증 이미지는 세무 요건이 아니라
  내부통제 요건
- 엔진은 한글 감열지에 강한 상용 OCR 또는 멀티모달 모델을 Phase 1에서 비교 선정

### 6.5 건전성 검사 (collector-sentry)

명시적 오류보다 위험한 것은 **정상 응답처럼 보이는데 내용이 비어 있는 조용한 실패**다.
카드사 사이트 개편 시 실제로 발생한다.

| 검사 항목 | 임계값 | 위반 시 |
|---|---|---|
| 수집 건수 0 | 0건 | 즉시 경보 + **독촉 카운트 중단** |
| 건수 급감 | 전주 동요일 대비 -70% 이하 | 경보 |
| 가맹점 사업자번호 결측률 | 10% 초과 | 경보 (국세청 연동 무력화 위험) |
| 금액 이상 | 0 또는 음수 존재 | 경보 |
| 카드번호 형식 불일치 | 마스킹 패턴 불일치 | 경보 (**필드 밀림 의심**) |
| 연속 실패 일수 | 롤링 범위의 절반(7일) 초과 | 별도 경보, 수동 소급 필요 |

## 9. 개발 범위

### 포함
카드 승인내역 자동 수집 배치(트랙 B) · 지출 등록 앱 + OCR 자동채움(트랙 A) ·
자동 매칭 엔진 및 수동 매칭 화면 · 룰엔진 + 국세청 사업자등록 상태조회 ·
검토·승인·보완 워크플로 · 알림(미제출 독촉, 보완요청, 마감) · 월마감 및 잠금,
취소·부분취소 조정 · 배치 건전성 검사 및 운영 모니터링

### 제외
- 전표 자동생성 및 회계 시스템 직접 연동 → **CSV/Excel 내보내기까지만**
- 부가세 신고서 자동 작성 → **불공제 판정 플래그 제공까지만**
- 카드사 승인 문자 자동 파싱 → 1차 범위 제외
- 개인카드·현금 지출 정산 → **분기 경로만** 만들고 실제 처리는 기존 방식 유지

## 10. 일정 (문서 기준)

| Phase | 내용 | 기간 | 주요 산출물 |

마쳐야 한다.

Phase 1 종료 시 의사결정 3가지
1. CODEF 계속 vs 카드사 EDI 전환 — 카드사 회신과 실측을 함께 놓고 판단
2. 가맹점 사업자번호가 채워지지 않으면 국세청 연동·불공제 자동판정을 범위에서 제외
3. 자동 매칭 성공률 90% 미만이면 매칭 키·허용오차 재설계 후 Phase 2 진행

## 13. 비기능 요구사항

- **보안**: 카드사 비밀번호·인증서 **평문 저장 금지**. RSA 암호화 전송 후
  `connectedId` 만 보관. 영수증 이미지는 본인·담당자·관리자만 접근.
  사용자별 지출 내역은 인사·노무 민감 정보이므로 열람 권한 최소화
- **감사**: 모든 상태 변경을 `review_log` 에 기록(누가·언제·무엇을·왜).
  카드내역 원본 수정 금지, 갱신 시 이력 추가 보관
- **성능**: 등록 화면 진입~촬영 1초 이내, OCR 비동기, 배치 1회 카드사당 5분 이내
- **가용성**: 연동 장애 시에도 트랙 A 정상 동작. 오프라인 촬영·입력 및 복구 시 자동 전송
- **보관**: 카드내역 원본·영수증 이미지 **최소 5년**, 배치 로그 1년
- **확장**: 수집 계층 인터페이스 분리(CODEF ↔ EDI 교체), 카드사 추가는
  `card_config` 등록만으로 대응

## 14. 크로스 통합관리시스템 관점의 확인 사항

문서 자체는 독립 시스템 기준으로 작성돼 있다. 크로스에 모듈로 얹으려면 아래
결정이 필요하다. **고객사 확인 대상이다.**

### 14.1 기존 기능과 겹치는 부분

| ECMS 설계 | 크로스 기존 | 확인 필요 |
|---|---|---|
| `site` 현장 마스터 (M-01) | PMS 프로젝트 마스터 | 문서에 "PMS 연계"로 돼 있음. **신설이 아니라 PMS 프로젝트를 그대로 쓰는 것으로 정리 필요** |
| M-03 사용자 · 권한 | 크로스 공통 인증 · 권한 | 별도 관리 vs 공통 사용 |
| M-04 감사 로그 | 크로스 공통 로그 | 별도 관리 vs 공통 사용 |
| `receipt` 영수증 이미지 보관 | DMS + Google Drive | 이미지 보관 위치·5년 보존 요건 반영 방식 |
| `account_code` 계정과목 | 공통코드 (`code_group.module`) | 공통코드 체계에 `ecms` 모듈로 수용 가능 |

### 14.2 아직 미확정인 사항

1. **카드사 미확정 · CODEF 미가입 · 카드사 계정 미확보** — Phase 0 가 끝나야
   실질 착수가 된다
2. **일정 합계 불일치** — Phase 표를 더하면 1+2+4+2+2+2+2 = **15주**인데
   본문은 "총 13주"로 적혀 있다. 확인 필요
3. **OCR 엔진 미선정** — Phase 1 비교 선정 대상. 비용 발생 항목
4. **CODEF 과금** — 응답이 있는 유효 호출만 1건 과금, 후불 익월 10일.
   카드 장수·현장 수에 따른 월 예상 비용 산정 필요
5. **모바일 앱 배포 형태** — PWA 기본이나, 크로스 포털과의 로그인 연계 방식 확인 필요
