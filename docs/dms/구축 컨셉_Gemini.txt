제시해주신 요구사항(기존 DB 유지, PMS/SMS/EMS/SWMS 통합, 5대 카테고리 기반 폴더링, 검색 및 발주처 대응 최적화)을 바탕으로 **「Cross 통합 문서관리 시스템(Cross-DMS) 구축 계획서」**를 제안합니다.
이 계획서는 **"물리적 데이터는 분산되어 있어도, 논리적 관리는 중앙에서 수행한다"**는 하이브리드 전략을 핵심으로 합니다.
Cross 통합 문서관리 시스템(Cross-DMS) 구축 계획서

1. 개요 및 목표
프로젝트명: Cross-DMS (Document Management System) 독립 모듈 구축
핵심 목표:
통합 검색: PMS, SMS, EMS, SWMS에 산재된 문서를 단일 접점에서 즉시 검색.
현장 대응: 현장 실무자가 문서를 쉽게 작성하고, 발주처 요청 시 관련 문서를 '원클릭'으로 패키징하여 제출.
기본 원칙: 기존 레거시(PMS/SMS/EMS/SWMS)의 DB 및 로직을 최대한 보존하면서, DMS라는 새로운 **'메타데이터 허브'**를 구축.

2. 시스템 아키텍처 (Hybrid DB 전략)
기존 DB를 살리면서 새로운 기능을 추가하기 위해 「가상화 계층(Virtualization Layer)」 방식을 제안합니다.

2.1. 데이터베이스 구조 (Legacy + New)
기존 DB (As-Is): PMS, SMS, EMS, SWMS 각 모듈의 첨부파일 테이블은 그대로 둡니다. (기존 업무 로직 파괴 방지)
신규 DMS DB (To-Be): 모든 문서의 '주소록' 역할을 하는 통합 인덱스 DB를 생성합니다.
필수 테이블: DMS_Total_Index
컬럼 구성:
UUID (고유값)
Source_System (출처: PMS, SMS 등)
Origin_ID (원본 테이블의 PK)
Category_Code (5대 대분류)
Project_ID / Client_ID (발주처)
Meta_Tags (검색용 키워드)

2.2. 모듈 독립성
Cross-DMS 모듈: 독립적인 웹/앱 인터페이스를 가집니다. 사용자는 개별 모듈(SMS 등)에 들어가지 않고 DMS에서 문서를 조회합니다.
API 연동: DMS에서 문서를 클릭하면, 원본 모듈(예: SMS)의 파일 저장 경로를 호출하여 다운로드/미리보기를 제공합니다.

3. 핵심 기능 정의
3.1. [목적 1] 검색 및 자료 활용 (Smart Retrieval)
기존에 공유해주신 '5개 대분류 + 프로젝트 + 고객사' 규칙을 **가상 폴더(Virtual Folder)**로 구현합니다.
다차원 분류 트리 (Dynamic Tree View):
물리적으로 폴더를 나누지 않고, 메타데이터 필터링을 통해 사용자가 보는 뷰를 동적으로 구성합니다.
예: [대분류: 안전] > [프로젝트: A건설] > [고객사: B공사] 순으로 클릭하여 접근.
통합 검색 엔진:
파일명, 등록자 뿐만 아니라 문서 내부 텍스트(OCR 적용 고려)까지 검색.
"최근 일주일 내 작성된 A프로젝트의 점검일지"와 같은 상세 필터 제공.

3.2. [목적 2] 현장 작성 지원 및 발주처 대응 (Fast Response)
현장에서 문서를 새로 만들고, 발주처 요구에 대응하는 프로세스를 자동화합니다.
템플릿 뱅크 (Template Bank):
5대 카테고리별 표준 양식(hwp, docx, xlsx)을 DMS에 등록.
현장 사용자는 '양식 다운로드 -> 작성 -> DMS 업로드' 과정을 통해 표준화된 문서 생산.
발주처 제출용 '원클릭 패키징' (Binder Generation):
기능: 발주처가 "지난달 안전 점검 관련 서류 일체 제출하세요"라고 요청 시.
동작: 검색 결과(예: 12월, 안전 카테고리)를 선택 후 [제출용 압축] 버튼 클릭 → 자동으로 폴더 구조가 잡힌 ZIP 파일 생성 또는 제출용 PDF 바인더 생성.
효과: 담당자가 일일이 파일을 찾아 폴더를 만들고 복사하는 시간(수 시간 소요)을 수 초로 단축.

4. 폴더 및 분류 체계 (Taxonomy)
공유해주신 규칙을 시스템 로직으로 확정합니다.
Level 1 (Root): 프로젝트 (Project)
현장/프로젝트 단위로 최상위 구분
Level 2: 5대 대분류 (Category)
(예시) ①공무/행정 ②공사/시공 ③안전(SMS) ④환경(EMS/SWMS) ⑤품질
※ 각 모듈(SMS, EMS 등)에서 생성된 문서는 자동으로 해당 대분류로 태깅되어 저장됨.
Level 3: 고객사/발주처 (Client/Stakeholder)
내부용 문서와 제출용(고객사별) 문서를 구분하는 태그.
Level 4: 문서 종류 (Doc Type)
보고서, 도면, 공문, 회의록 등

5. 단계별 구축 로드맵
Phase 1: 기반 구축 (DB & Migration)
DMS 전용 DB 스키마 설계: DMS_Index 및 분류 코드 테이블 생성.
데이터 마이그레이션 (동기화): 기존 PMS/SMS/EMS/SWMS에 있는 파일 정보를 읽어와 DMS 인덱스 테이블에 매핑(Mapping)하는 배치 프로그램 개발.
Phase 2: 핵심 기능 개발 (Search & View)
UI/UX 개발: 5대 카테고리 기반의 탐색기(Explorer) 형태 UI 구현.
뷰어 연동: 다양한 포맷(CAD, PDF, Office)의 문서를 웹에서 바로 보는 통합 뷰어 연동.
Phase 3: 활용성 고도화 (Action)
템플릿/작성 기능: 현장 태블릿 등에서 바로 양식을 불러와 작성하는 기능.
패키징 기능: 선택 문서를 고객사 제출 포맷으로 자동 변환/압축하는 모듈 개발.

**프로젝트(Project)**와 **고객사(Client/발주처)**의 구분은 시스템 설계 단계에서 **'데이터 관계(Relation)'**와 '사용자 경험(UI/Folder)' 두 가지 측면에서 명확히 정의해야 혼란이 없습니다.
제안해주신 5대 카테고리 운영 방식을 고려하여, Cross-DMS에서 두 요소를 구분하고 연결하는 구체적인 기준을 정리해 드립니다.

1. 개념적 구분 (정의)
가장 먼저 시스템 내부 용어 정의를 확립해야 합니다.
프로젝트 (Project):
성격: **'행위(Activity)와 현장'**의 단위. 시작일과 종료일이 있고, 특정 목표(완공, 납품)가 있는 작업 공간입니다.
식별: 프로젝트 코드 (예: PJ-2024-001), 현장명.
예시: 평택 P4 신축공사, 서초동 사옥 리모델링, A지구 안전진단 용역.
고객사 (Client/발주처):
성격: **'주체(Entity)'**의 단위. 프로젝트를 발주하거나 돈을 지불하는 대상(회사)입니다. 하나의 고객사는 여러 프로젝트를 발주할 수 있습니다.
식별: 사업자번호, 고객사 코드 (예: CL-SAMSUNG), 회사명.
예시: 삼성물산, 현대건설, LH공사, 서울시청.

2. 시스템적 구분 (DB 및 로직 설계)
DB에서는 1:N (일대다) 관계로 관리하는 것이 가장 효율적입니다.
A. 마스터 데이터 분리
고객사 마스터 (Client Master): 고객사 정보를 관리하는 기준 테이블입니다. (한 번 등록하면 계속 사용)
프로젝트 마스터 (Project Master): 프로젝트를 생성할 때, **'이 프로젝트의 고객사는 누구인가?'**를 선택하여 매핑합니다.
B. 데이터 구조 (예시)
[Rule] 하나의 프로젝트는 반드시 하나의 메인 고객사(발주처)를 가집니다. (단, 수신처는 다를 수 있음)
Project_Table
Project_ID: P240101 (PK)
Project_Name: 강남 오피스 구축
Client_ID: C001 (FK - 고객사 테이블 참조)
Client_Table
Client_ID: C001 (PK)
Client_Name: (주)Cross건설
Biz_Type: 민간

3. 문서관리(DMS)에서의 활용 구분 (폴더/뷰)
사용자가 문서를 찾을 때 프로젝트와 고객사를 어떻게 구분해서 보여줄지가 핵심입니다. **[프로젝트 중심 뷰]**를 기본으로 하되, 분류 목적으로 고객사를 활용하는 것을 추천합니다.
방안 1: 프로젝트 우선 (Project-First) -> 추천
현장 실무자가 가장 선호하는 방식입니다.
구조: [1.프로젝트] > [2. 5대 카테고리] > [3. 상세폴더]
고객사의 역할: 프로젝트의 속성(Attribute)이자 검색 필터.
시나리오:
사용자는 **'서초동 사옥 프로젝트'**를 먼저 선택해서 들어갑니다.
그 안에서 '안전(SMS)' 카테고리를 누릅니다.
문서 리스트를 볼 때 [고객사 제출용] 태그가 붙은 문서만 필터링하거나, 별도의 **'발주처 송부 폴더'**를 둡니다.
방안 2: 고객사별 분류 (Client-First)
본사 관리자나 영업팀이 선호하는 방식입니다.
구조: [1. 고객사] > [2. 프로젝트 리스트] > [3. 문서]
시나리오:
관리자가 '삼성물산' 폴더를 클릭합니다.
삼성물산과 진행했던 과거 10년 치 프로젝트(A현장, B현장, C현장)가 모두 나옵니다.
특정 프로젝트를 선택해 문서를 확인합니다.

4. Cross-DMS를 위한 최적화 제안 (Cross Specialness)
작성해주신 **"발주처 대응"**이라는 목적을 달성하기 위해, 다음과 같은 '태그(Tag)' 방식의 구분을 제안합니다.
폴더 구조는 [프로젝트] 중심으로 가되, 문서를 등록할 때 [제출처]를 태깅합니다.
문서 등록 시:
사용자가 '위험성평가표'를 업로드합니다.
시스템이 묻습니다: "이 문서는 내부용입니까, 고객사(삼성물산) 제출용입니까?"
[제출용] 체크 시 -> Client_Share 속성이 True가 됨.
활용 시 (Virtual Folder):
평소에는 프로젝트 > 안전 폴더에서 모든 문서를 관리합니다.
감사/점검 시 [고객사 바인더 보기] 버튼을 누르면, 시스템이 Client_Share가 체크된 문서만 모아서 가상의 **'제출용 폴더'**를 보여줍니다.
요약하자면:
DB: 고객사와 프로젝트는 별도 테이블로 관리하되 연결(Mapping)한다.
폴더: 프로젝트를 최상위 폴더로 둔다.
구분: 문서의 속성(내부용 vs 고객 제출용)으로 고객사 관련 문서를 구분한다.

* *용도:* "작년에 '콘크리트 강도' 관련 이슈 있었던 문서 찾아줘"라고 할 때 유용합니다. (Elasticsearch 등의 엔진 활용 고려)

3. **기간 범위 검색**
* "지난달(12월 1일 ~ 31일)에 작성된 문서 중 '부적합 보고서'만 조회"

### 3. 문서의 계층 구조 관리 (공식 명칭 vs 하부 문서)
현장 문서는 **'단일 문서'**도 있지만, 말씀하신 대로 **'세트(Set)'**로 움직이는 경우가 많습니다. 이를 물리적 폴더 안에 또 폴더를 만드는 방식(Depth가 깊어짐) 대신, **「문서 그룹(Document Grouping)」** 개념으로 관리하는 것을 추천합니다.
#### Case 1: 단독 문서 (Independent Doc)
* **예:** 공문, 회의록, 단순 사진대지.
* **관리:** 그냥 파일 1개로 등록.
#### Case 2: 상위-하위 관계 (Parent-Child)
* **상황:** `[상위] 위험성평가 계획서`가 있고, 그 아래에 매주 업데이트되는 `[하위] 주간 위험성평가표`들이 계속 붙는 경우.
* **해결책: 「바인더(Binder)」 또는 「시리즈(Series)」 기능**
* DMS에서 **'위험성평가(2026)'**라는 가상의 **바인더**를 하나 만듭니다.
* 최초의 '계획서'를 여기에 등록합니다.
* 이후 발생하는 '결과서', '회의록'을 등록할 때 **"이 문서는 '위험성평가(2026)' 바인더에 포함된다"**라고 연결합니다.
* **조회 시:** 사용자는 '위험성평가(2026)' 하나만 클릭하면, 그 안에서 계획서와 그동안 누적된 결과서들이 타임라인 순으로 정리되어 보입니다.
#### Case 3: 공식 명칭과 첨부자료 (Attachments)
* **상황:** `품질계획서` (메인 파일) + `시험성적서`, `장비리스트`, `자격증사본` (근거 자료들).
* **해결책: 메인 문서와 첨부 파일**
* 게시판 글쓰기와 같습니다. **메인 파일(Master File)**은 '품질계획서.hwp' 입니다.
* 나머지는 **첨부 파일(Ref Files)**로 등록합니다.
* 검색 결과에는 '품질계획서'만 대표로 노출되고, 클릭하면 첨부파일 목록이 뜹니다.

### [정리] 시스템 구현 시나리오
1. **프로젝트 시작:** PMS에서 `서초동 사옥(P-001)` 생성 → DMS 자동 연동.
2. **문서 작성:** SMS 모듈에서 `위험성평가 1회차` 작성.
* 메타데이터 자동 태깅: `Project: P-001`, `Category: 안전`, `Type: 결과보고서`, `Client_Submit: Y`
3. **문서 연결:** "이 문서는 `초기 위험성평가 계획서`의 하위 문서임" 설정.
4. **발주처 요청 시:**
* DMS 검색창에서 필터: `[프로젝트: 서초동]`, `[고객제출: Y]`, `[문서명: 위험성평가]`
* **결과:** 계획서와 1회차 결과보고서가 세트로 묶여서 조회됨 → **[일괄 다운로드]** 클릭.

이 방식(바인더/그룹핑)을 도입하면 폴더 깊이를 3단계 이상 늘리지 않으면서도 수천 개의 문서를 체계적으로 관리할 수 있습니다.

1. [정리] Cross-DMS 구축 정의서 (Summary)
이 내용은 프로젝트의 Master Plan 역할을 합니다.

1.1. 시스템 개요
시스템명: Cross-DMS (Document Management System)
목적: PMS/SMS/EMS/SWMS에 산재된 문서를 통합 관리하고, 현장 작성 및 발주처(Client) 대응 업무를 자동화함.
핵심 전략:
Hybrid DB: 기존 모듈(Legacy)의 DB는 유지하되, DMS 전용 **'메타데이터 인덱스 DB'**를 신설하여 논리적으로 통합.
Virtual Folder: 물리적 폴더가 아닌, 메타데이터(프로젝트+카테고리+고객사) 조합을 통한 가상 폴더 뷰 제공.

1.2. 데이터베이스 모델링 (PostgreSQL 기준)
Legacy 연동: 기존 PMS, SMS 등의 파일 테이블 PK를 참조(Reference)만 함.
신규 테이블 구조:
DMS_Index_Master (핵심): 모든 문서의 메타데이터 저장소 (UUID, 출처, 원본ID, 제목, 태그 등).
DMS_Binder_Group: 문서를 시리즈(계획서-결과서)나 세트로 묶는 논리적 그룹.
Project_Master & Client_Master: 프로젝트와 고객사를 1:N 관계로 정의.

1.3. 핵심 로직 및 기능
분류 체계 (Taxonomy):
Level 1: Project (최상위)
Level 2: Category (5대 대분류: 공무/공사/안전/환경/품질)
Level 3: Client View (발주처 제출용 태그 필터링)
검색 (Retrieval):
Faceted Search: 카테고리, 날짜, 제출여부(Client_Submit=Y)를 조합한 다중 필터 검색.
발주처 대응 (Packaging):
특정 프로젝트의 특정 기간 내 Client_Submit=Y인 문서만 추출하여 ZIP/PDF 바인더로 자동 생성.
